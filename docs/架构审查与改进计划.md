## 一、现状架构总览

### 1.1 技术栈与代码规模

| 层次 | 实现 | 规模 | 评价 |
| :--- | :--- | :--- | :--- |
| 路由/静态服务 | `server.py`（标准库 `http.server`） | 420 行 | if-elif 手工路由，无框架 |
| 核心分析引擎 | `main.py`（CLI 子进程方式被调用） | 1869 行 | 三家模型（Kimi/Qwen/Gemini）逻辑混杂于单文件 |
| 业务服务层 | `backend/service_*.py` | 各 5~28KB | 边界基本清晰 |
| 数据层 | `backend/app_db.py`（MySQL/SQLite 双实现） | 25KB | 仅 `users`、`detection_history` 两张表 |
| 前端 | `web/assets/app.js`（单文件） | 4201 行 / 140KB | 所有页面逻辑集中一个文件 |
| 结果存储 | 文件系统（`result/*.md|json|mp4`） | — | 不入库、无元数据、无归属 |

### 1.2 核心数据流

```
浏览器(app.js) → server.py → service_analyze(线程+信号量限流)
    → subprocess main.py → Kimi/Qwen/Gemini API
    → result/*.md + *.json → 前端轮询 /api/task_status → review.html 渲染
```

### 1.3 现有功能清单

- 登录鉴权（Bearer Token）、用户管理（admin/user 两角色）
- 视频上传（截断 180s、720p 压缩）、3FPS 拆帧
- 多模型分析（Kimi 分批发帧 / Qwen 视频直传 / Gemini）、任务进度轮询
- 结果查看（视频播放器 + 动作表 + 时间轴联动 + 统计图 + 建议）
- 动作表人工修订（回写 Markdown/JSON）、SOP 注入 Prompt、中英翻译
- 费用计算器、检测历史

## 三、架构重构建议

### 3.1 总体方向：小步演进，而非推倒重来

当前"标准库 HTTP + 文件存储"在单机内网场景其实是合理的取舍。建议分两条线：

- **不换框架线（保守）**：保留 `http.server`，引入路由表 + 中间件管道，工作量小、风险低。
- **换框架线（推荐）**：迁移 **FastAPI**。理由：自动 OpenAPI 文档、pydantic 校验、原生后台任务、WebSocket 支持（进度推送）、社区成熟。`service_*.py` 业务函数基本可以平移。

无论哪条线，以下分层重构是共同的：

```
backend/
├── api/            # 路由层：只做参数解析与响应封装
├── services/       # 业务层：项目/产线/任务/结果/用户
├── providers/      # 模型适配层：kimi.py qwen.py gemini.py + base.py
├── repositories/   # 数据访问：全部 SQL 集中于此
├── core/           # 配置、日志、鉴权、异常
└── tasks/          # 任务队列与状态机（持久化到 DB）
```

### 3.2 关键重构点

1. **任务系统持久化**（对应 P0-4/14）
   新建 `tasks` 表：`id, user_id, video_id, project_id, line_id, model, status(pending/running/succeeded/failed/canceled), progress, progress_total, phase, error, token_usage, created_at, started_at, finished_at`。后台线程从表中取任务；重启时把 `running` 任务标记为 `failed(interrupted)`，前端不再出现僵尸任务。

2. **结果元数据入库**（对应 P0-2）
   新建 `analysis_results` 表：`id, task_id, video_id, project_id, line_id, md_path, json_path, video_copy_path, en_md_path, stats_json, version, created_by, created_at`。文件仍存 `result/`，但列表、检索、权限、统计全部走 DB。文件系统退化为纯存储。

3. **模型 Provider 层**（对应 P2-15）
   把 `main.py` 拆为：`prompt.py`（prompt/schema/合并）、`media.py`（抽帧/编码/压缩）、`providers/*`（每家一个文件，实现统一接口 `analyze(frames|video, prompt, key) -> ModelOutput`）、`cli.py`（兼容现有子进程调用方式，可渐进迁移为进程内调用）。

4. **前端模块化**（对应 P2-16）
   将 `app.js` 拆为 `api.js / auth.js / detection.js / review.js / users.js / settings.js / i18n.js`，用原生 ES modules 即可，不必强制引入构建链。后续若做结果查看增强（见第五节），建议引入 Vite + 一个轻量组件方案。

## 四、「项目 / 产线」组织层级设计（核心新增功能）

### 4.1 领域模型

```
项目 Project (1) ──< 产线 ProductionLine (1) ──< 工位 Station(可选)
     │                      │
     └──< 项目成员 Member    └──< 视频 Video ──< 分析任务 Task ──< 结果 AnalysisResult
```

### 4.2 数据库变更（DDL）

```sql
CREATE TABLE projects (
    id INT AUTO_INCREMENT PRIMARY KEY,
    code VARCHAR(32) NOT NULL UNIQUE,          -- 项目编号，如 PRJ-A01
    name VARCHAR(128) NOT NULL,
    description TEXT,
    status VARCHAR(16) NOT NULL DEFAULT 'active',   -- active/archived
    created_by INT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE production_lines (
    id INT AUTO_INCREMENT PRIMARY KEY,
    project_id INT NOT NULL,
    code VARCHAR(32) NOT NULL,
    name VARCHAR(128) NOT NULL,                -- 如 "总装一线"
    process_desc TEXT,                         -- 工艺描述，可注入 Prompt 上下文
    sop_content MEDIUMTEXT,                    -- 产线级 SOP（替代全局单文件 SOP）
    status VARCHAR(16) NOT NULL DEFAULT 'active',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uq_line (project_id, code),
    FOREIGN KEY (project_id) REFERENCES projects(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE project_members (                  -- 项目级权限
    project_id INT NOT NULL,
    user_id INT NOT NULL,
    role VARCHAR(16) NOT NULL DEFAULT 'member', -- owner/editor/viewer
    PRIMARY KEY (project_id, user_id),
    FOREIGN KEY (project_id) REFERENCES projects(id),
    FOREIGN KEY (user_id) REFERENCES users(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 既有表扩展
ALTER TABLE users ADD COLUMN org_path VARCHAR(255) DEFAULT NULL;  -- 可选：所属组织
ALTER TABLE detection_history ADD COLUMN project_id INT NULL, ADD COLUMN line_id INT NULL, ADD COLUMN task_id INT NULL;

CREATE TABLE videos (                           -- 新增：视频资产表（替代裸目录扫描）
    id INT AUTO_INCREMENT PRIMARY KEY,
    project_id INT NOT NULL,
    line_id INT NULL,
    filename VARCHAR(255) NOT NULL,
    stored_path VARCHAR(512) NOT NULL,
    duration_sec DOUBLE,
    size_bytes BIGINT,
    uploaded_by INT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_video_scope (project_id, line_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

> 迁移策略：旧数据归属到一个自动创建的"默认项目 / 默认产线"，通过脚本把 `data/`、`result/` 现有文件登记入库，保证向后兼容。

### 4.3 API 设计

| 方法 | 路径 | 权限 | 说明 |
| :--- | :--- | :--- | :--- |
| GET/POST | `/api/projects` | 登录（按成员过滤）/ admin | 项目列表 / 创建 |
| GET/PUT/DELETE | `/api/projects/{id}` | 成员 viewer / owner | 详情（含产线数、视频数、最近任务）|
| GET/POST | `/api/projects/{id}/lines` | editor | 产线列表 / 创建 |
| PUT/DELETE | `/api/lines/{id}` | editor | 产线编辑（含 SOP 维护）|
| POST/DELETE | `/api/projects/{id}/members` | owner | 成员管理 |
| GET | `/api/projects/{id}/stats` | viewer | 项目级统计（任务量、Token 消耗、动作分布）|
| 调整既有接口 | `/api/upload`、`/api/analyze`、`/api/list_results`、`/api/user_history` | — | 增加 `project_id`/`line_id` 参数，返回按成员权限过滤 |

权限规则：admin 全量；项目 owner 管理成员与产线；editor 可上传/发起分析；viewer 只读。

### 4.4 前端交互设计

1. **全局作用域选择器**：顶栏增加「项目 ▾ / 产线 ▾」级联下拉，存入 localStorage，所有页面（检测、结果、历史、统计）默认跟随该作用域过滤。
2. **新增「项目管理」页**（admin/owner）：项目卡片 + 产线表格 + 成员管理弹窗 + 产线 SOP 编辑（迁移现有 SOP 弹窗，实现 SOP 按产线隔离——这是产线层级的直接业务价值：不同产线不同 SOP 注入不同 Prompt）。
3. **检测页**：上传与发起分析必须选择产线；历史列表按当前作用域过滤。
4. **SOP 机制升级**：`data/SOP.md` 全局文件 → `production_lines.sop_content` 字段，分析时按任务所属产线注入。

## 五、结果查看体验增强设计

现状（`review.html`）：视频播放器 + 动作表 + 时间轴联动 + Chart.js 柱状图 + Markdown 面板 + 上下文菜单编辑。基础已具备，按以下优先级增强：

### 5.1 P0 — 核心体验

1. **动作帧缩略图**：分析阶段每条动作保存起止时刻的抽帧缩略图（抽帧已有，补一个"按动作区间存图"步骤），动作表每行显示首帧缩略图，点击即跳转播放。**这是对"结果可读性"提升最大的一项。**
2. **可交互时间轴条**：将现有时间轴升级为横向色带图（每类动作一个颜色，按时间区间绘制 Canvas/SVG 条），支持：点击定位、拖拽悬停预览、区间缩放（针对密集动作）。
3. **统计增强**：柱状图之外增加——动作时长占比环形图、VA/NVA（增值/非增值）分类统计条（字段已有 `value_added`）、单动作时长分布箱线图；支持按产线聚合的**跨视频对比视图**。

### 5.2 P1 — 分析工作台

4. **结果版本对比**：同一视频多次分析（不同模型/参数）并排对比动作表差异（DB 化后天然支持 `version` 字段）。
5. **编辑体验**：动作行内编辑（替代弹窗）、动作拖拽调序、时间轴上直接拖拽调整起止点、编辑历史留痕（`result_revisions` 表，可回滚）。
6. **导出**：一键导出 Excel/CSV（动作表+统计）、导出含缩略图与图表的 PDF/HTML 报告，供产线评审会使用。

### 5.3 P2 — 管理驾驶舱

7. **项目/产线仪表盘**：任务量趋势、Token/费用消耗（`detection_history` 已有 token 字段）、高频动作 TopN、平均周期时间（CT）趋势——数据入库后均为简单聚合查询。

## 七、风险与注意事项

1. **兼容迁移**：老用户已有 `data/`、`result/` 文件必须能一键登记进默认项目，否则升级即"数据丢失"观感。
2. **截断策略变更**是行为变化：180s 截断改分段分析会显著增加 Token 成本，需给用户开关与预估提示。
3. **多模型 Provider 抽取**时保持 CLI 子进程兼容（`service_analyze.py` 现以 stdout JSON 事件解析进度），建议先在子进程协议稳定后再切进程内调用。
4. **SQLite 支持取舍**：若目标环境明确 MySQL，建议砍掉双实现（app_db.py 体积可减半）；若坚持轻量单机，则反向砍掉 MySQL。双轨并存是长期维护负担。
5. **依赖与运维约束**（来自 `docs/rules.md`，实施时必须遵守）：
   - MySQL 连接必须使用 `127.0.0.1` 且 root 开密码认证，禁用 `localhost`（避免 socket 认证导致 1698 错误）——`app_config.py` 现有默认值已正确，勿在重构中回退。
   - NumPy 必须锁版本 `< 2.0.0`（`requirements.txt` 已锁），避免与 OpenCV 等预编译库二进制冲突；任何依赖升级需连带验证 `import cv2` 可用。
   - Docker 构建历史遗留坑（见 `version.md` v10.6.x 系列）：PEP668、pip/wheel 卸载冲突、镜像源超时——阶段 4 改造镜像时保留 `docker/build_docker.sh` 中已验证的规避方案。
